# Protocol references

Third-party GP-5 / GP-50 web editors that already solve connect, dump, and live control.

**Read** the local copy in `reference/` (GP-50 editor HTML) when encoding or decoding SysEx. Do **not** paste that JavaScript into `src/`. Implement Patone-owned codecs; match operator captures and Patone Log.

Useful observations (not a protocol spec):

- After connect they show a loading overlay (`Syncing with GP-50 …` / GP-5) and request a patch-name list, then the current patch index, then the current preset, then other dumps. Patone requests the IR-name dump and the globals dump once per connect (GP-50 and GP-5) after the current-preset ask, and does not wait on either. Preset-status and NAM stay out. On patch change they request that preset dump again; Patone does not re-request IR names or globals on Reload or patch change.
- Those asks share the identity-family SysEx template Patone already owns: name-list is size `0x0E` / command `0x00`, current-patch is size `0x07` / command `0x03`, current-preset is size `0x09` / command `0x01`. The IR-name request is the same 14-byte envelope with a distinct size and path: `F0 02 09 00 01 00 00 00 02 01 02 02 00 F7`. The globals request, shared by GP-50 and GP-5, is `F0 0B 09 00 01 00 00 00 02 01 02 01 00 F7`. A GP-50 Bluetooth Patone capture of size `0x0E` / command `0x01` only returned a 16-byte ACK, not a dump.
- Inbound current-preset fragments differ by pedal and link. Bluetooth GP-50 uses command `00 06` (short terminator); GP-5 uses `00 05`. USB GP-50 uses `01 0B` (data length 48, last fragment index 26). USB GP-5 uses `01 09` with data length exactly 48 and terminator length exactly 34 (reference `gp5usb.html`; do not treat other short lengths as end-of-dump). Name-list dumps stay `01 05` (Bluetooth) / `06 0A` (USB) and must not be parsed as a chain.
- Bluetooth IR-name fragments use command `00 04` (F0-aligned lengths 210 data / 94 terminator; the reference editor's raw packets are 212 / 96 including the BLE-MIDI header). Twenty nibble-packed names start at payload offset 44 with stride 32. They must not be fed to the current-preset assembler. USB IR fragments (GP-50 and GP-5 reference editors) are complete SysEx, command `01 02`, length 48, index nibbles at bytes 5–6, 38-byte payload from byte 9. The last fragment is index `0x11`. The concatenated payload uses the same name table. A blank or missing name keeps `User IR 01`…`User IR 20`. Do not paste `reference/` JavaScript.
- Bluetooth globals dump: F0-aligned length 210, command `00 02`, path `01 02 01` (reference editor BLE-wrapped length 212). Field offsets follow that editor packet (F0-aligned): master nibble at 63, input at 73, No CAB byte at 84, REC at 103, BT at 113, monitor at 123, REC mode L/R bytes at 134/144, footswitch byte at 194. Confirm against a Patone Log when one lands; do not paste editor source.
- USB globals dump (`_reference/GP50-USB.html`): fragmented SysEx, command `00 08` or `00 09`, data length 48 / terminator 20 or 22. Concatenate each fragment’s payload from byte 9; table offsets are the Bluetooth absolute offsets minus 9 (master 54, input 64, No CAB 75, REC 94, BT 104, monitor 114, REC mode L/R 125/135, footswitch 185). The reference editor’s `GLOBALcab = data[64]` reuses the input offset and is wrong; Patone uses 75. Patone asks for globals (and IR names) after the first current-preset dump lands, not in the same burst as the preset ask—USB overlaps those dumps otherwise. Fragments must not feed the current-preset assembler. Do not paste editor source.
- GP-5 globals dump (`_reference/GP5bluetooth.html`, `_reference/gp5usb.html`): same ask as GP-50. Bluetooth is one SysEx, F0 length 164, command `00 01`, path `01 02 01` (editor index minus 2): global volume nibbles at 53, screen brightness at 79, input at 89, REC at 99, monitor at 109, BT REC at 139, No CAB byte at 150, footswitch byte at 160. USB is fragmented SysEx, command `00 05`, data length 48 / terminator 12; payload offsets are those F0 offsets minus 9 (screen brightness at 70 is derived; the USB editor does not read it). A short or out-of-range screen byte leaves only screen brightness unknown. Do not parse a GP-50 globals payload as GP-5, or the reverse. Do not paste editor source.
- GP-50 global SysEx writes use packed family `1111` (`01 00 0a 11 11` + effect/flag + value), path `01 01 04`, CRC-8 + nibble-expand. Master volume is official CC 1 (0–100); Patch | Stomp is official CC 28 (0 / 127). Relative master step CC 17 stays unused. Bluetooth may apply live global notifies and inbound CC 1 / CC 28; USB must not. REC mode Dry/Wet wire polarity follows the reference editor's live label (0 = Dry) pending a Patone accept capture.
- GP-5 global writes use that same `1111` framing with GP-5 pairs: global volume effect 2 / flag 2 (0–100, not CC 1), input 1/3, No CAB 3/3, REC 1/4, BT REC 5/4, monitor 2/4, screen brightness 3/2 (1–100). Footswitch is packed family `1115` (`01 00 04 11 15 00` + mode 0–4: `0-99`, `0-9`, `A-Z`, `CTL`, `Tuner`), not CC 28 and not the GP-50 pairs (GP-50 BT REC 2/4 is GP-5 monitor; GP-50 REC mode right 5/4 is GP-5 BT REC). Bluetooth applies the GP-5 live map (24-byte notify, length-30 global volume, length-18 footswitch). There is no live screen-brightness packet. USB must not apply those reports. Inbound CC 1 and CC 28 must not change GP-5 globals. REC mode and Global BPM stay out on GP-5.
- USB uses Web MIDI with SysEx enabled. Some live global/footswitch changes are not notified over USB.
- Bluetooth uses the BLE-MIDI GATT service and the same SysEx conversation, wrapped in BLE-MIDI packets. Host SET SysEx is one GATT write (`80 80` + full `F0`…`F7`), as in the accepted chain-order capture. Do not chunk a 38-byte `1147`/`1148` SysEx into 20-byte packets; the pedal ignores that.
- **Two families:** identity / live notify uses path `01 02 04` (checksum unknown). Parameter **SET** uses path `01 01 04`, CRC-8 ATM (poly `0x07`, init 0) of the packed body, then nibble-expand each hex digit to a `0x0n` MIDI byte (`src/device/sysex-nibble.ts`). Echoing a live notify is not a SET.
- Pedal chain-order **notify** (Patone Log, Bluetooth): size `0x0C` / command `0x04` / path `01 02 04`, 34 bytes, nibble-expanded `DUMP_MODULE_IDS` indices. Patone GP Studio applies it on Bluetooth (`liveFromPedal`). USB does not emit it and must not apply it.
- Pedal chain-order **SET** (accepted operator log, Bluetooth, PRE before NR): same 10-slot payload, path `01 01 04`, CRC `08 07` for that order. Packed body `01 00 0C 11 44` + ten dump indices. W1 (host `01 02 04`) and W2 (notify echo, checksum `00 00`) were ignored. Notebook: `openspec/changes/chain-reorder/spike-chain-order-write.md`.
- Current-preset **model + control** fields live in that same dump (wire identity + float32 LE per kind). App→pedal model write is packed family `1147`; control write is `1148`. Same CRC-8 + nibble-expand SET path `01 01 04`. Pedal→app live model is identity-family command `07`; live control is command `08` (path `01 02 04`). Patone GP Studio applies those on Bluetooth (`liveFromPedal`) and ignores them on USB. The reference editor debounce is 50 ms on slider `input`. Patone GP Studio updates the snapshot on every step and coalesces the `1148` SET (~80 ms throttle, flush on pointer-up) so BLE-MIDI is not flooded. Do **not** copy `reference/` JavaScript; match captures.
- Storing the working patch (Save / rename / duplicate onto another slot) is a parameter-write SET of packed family `114a` (path `01 01 04`, CRC-8 ATM + nibble-expand; not live notify `01 02 04`). Packed body carries destination slot 0–99 and a 10-character space-padded ASCII name. Operator capture: Save and duplicate-to-another-slot both store that destination index (not a display-only field). Do not encode a full preset dump if that SET is ignored. Patone GP Studio **download** encodes a Valeton `.prst` for the connected model from the assembled current-preset dump. Layout locked from `_reference/gp50_60-TOB.prst` / `_reference/gp5_60-TOB.prst`: 20-byte ASCII model header (`GP-50` / `GP-5` padded + `01 00`), CRC-8 ATM (poly `0x07`, init 0) of the rest, spacer `FF FF FF FF`, 10-byte NUL name (spaces as `00`), model descriptor, packed dump body. GP-50 descriptor follows the capture (not the truncated HTML constant). Patone GP Studio **upload** is the inverse of that layout into the working patch: decode the file, apply with owned working-buffer writes (model `1147`, catalog-control `1148`, chain-order SET, module CC 48–57). It does not send store `114a` and is not a dump SET. Save / rename / duplicate remain the store. Apply paces those SysEx (short gap after each write, longer after a model SET and before the dump refresh) because USB `send` and BLE-MIDI `writeValueWithoutResponse` both return before the pedal has applied the previous message; a burst drops trailing writes. Packed family `1142` patch volume/BPM (descriptor fields; dump words before the packed body) follows the reference black-box `sendPatchVol` / `sendBPM` body (`01 00 0a 11 42`…) and is sent as part of apply; there is no Patone accept capture yet. That SET stays the upload path for volume and for BPM 40–255. BPM 256–260 cannot fit in that one-byte SET, so upload sends official CC 73 then CC 74 for those values. The patch bar does not use `1142`: live volume is official CC 7 (0–100) and GP-50 tempo is official CC 73 then CC 74 (40–260). Inbound CC 7, CC 73, and CC 74 are not applied to the snapshot. Bluetooth live patch-volume SysEx (size `0x07`, path `01 02 04`, preset-volume body) is applied to the snapshot; USB ignores it. After a patch change, the confirmation dump refreshes patch volume/BPM even when the chain already matched (Bluetooth first dumps are often stale for those words). Do **not** copy `reference/` source or payloads.

Movable chain modules: NR, PRE, MOD, DLY, RVB. DST, NS, AMP, CAB, EQ stay a contiguous block.

Patone GP Studio’s in-scope subset is current patch index, onboard names, the current preset’s audio chain (module order + on/off + factory model and control values for the ten effect slots, including the twenty user-IR CAB slots, plus stomp assignment masks), the IR-name dump, the shared globals ask and the GP-50 and GP-5 dump decodes (offsets from the reference editors), Bluetooth live chain-order follow, Bluetooth live model/control follow, Bluetooth live global follow, the order-only SET, model/control SETs of the same parameter-write family (`1147` / `1148`, including selecting a user IR slot), stomp-assignment SETs (`114d`), global SysEx SETs (`1111`, plus GP-5 footswitch `1115`), GP-50 master volume (CC 1) and Patch | Stomp (CC 28), GP-5 global volume and the five GP-5 footswitch modes, tuner on/off (CC 58), the current-patch store SET (`114a`), a connected-model Valeton `.prst` export of that dump, and current-patch `.prst` load into the working patch (inverse of the locked layout, owned writes, not a dump SET and not a store). Library browse/import/reorder, Library `.prst` import, cross-model conversion, IR / NAM **file upload**, the Editor route, and an in-app pitch display stay out. GP-5 REC mode, CC 1, CC 28, and Global BPM stay out. Patch-bar volume (CC 7) and GP-50 BPM (CC 73/74) are in scope on USB and Bluetooth; inbound volume, BPM, and tuner CC are not applied.

Tuner **on/off** is official MIDI CC 58: write 127 to enter and 0 to leave (same bands as module on/off). The session tracks the last app write only; inbound CC 58 is ignored. No pitch UI in Patone. A patch change (app recall or pedal current-patch) sends CC 58 = 0 when the tuner was on.

Stomp **press** (stepping the footswitch from the app) is official MIDI CC, value 127, one message: GP-5 and GP-50 A are CC 69; GP-50 B is CC 70. The session toggles each assigned effect on-change and does not send module CC 48–57, family `114d`, patch recall, or a chain dump for that press. USB still ignores live stomp reports. Bluetooth command `0E` may replace that on/off with the pedal's mask.

Stomp **assignment** (which modules each footswitch toggles) is in scope. Dump masks use the same enable-style nibbles as module on/off: GP-50 stomp 1 at 1006/1007/1009 and stomp 2 at 1014/1015/1017; GP-5 single stomp at 920/921/923. EXP is never in the mask. App→pedal write is packed family `114d` (size `0x0A`, path `01 01 04`, CRC-8 ATM + nibble-expand): dual-mask body A then B (GP-5 B empty). Pedal→app live command `0D` is notify-only; do not apply it on USB; do not apply it on Bluetooth until a Patone `114d` SET is accepted. Failed guessed envelopes stay in `openspec/changes/archive/2026-09-23-stomp-assignment/spike-assignment-write.md`. Do **not** copy reference JavaScript or hex payloads.
